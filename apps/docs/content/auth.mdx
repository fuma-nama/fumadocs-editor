## The trust model

No `authenticate` hook: the sync server allows everything, same as Vite's
dev socket. Anyone who can reach the server can edit. Fine for local
development, not for anything shared. Passing `authenticate` puts every
surface behind your policy.

Enforcement is **server-only**. The client sends credentials and exposes
what the server decided. It does not change its own behavior. Wiring "this
user can't write" into a read-only editor is [your code](/read-only).

## The two hooks

**Server**: `authenticate` maps a connection (or media request) to a scope,
or `null` to reject. Once per websocket (again on reconnect, so refreshed
tokens apply) and once per HTTP media request.

**Client**: transport `auth` produces an opaque payload on every connection
attempt. It is sent on the first frame (browser websockets cannot set headers;
query strings leak into logs) and the `x-fde-auth` header (`AUTH_HEADER`)
on media requests. Cookie setups omit it and read the request server-side.

## The scope contract

```ts
interface SyncScope {
  user?: { name: string; color?: string };
  read?: boolean | ((path: string) => boolean); // default true
  write: boolean | ((path: string) => boolean);
}
```

A document is its root-relative posix path. Predicates are per-document
permissions. Every predicate sees the **normalized** relative path, so
`team-a/../outside.mdx` cannot write past a `team-a/` rule. Predicates run
on the message hot path and must be synchronous: resolve async policy
inside `authenticate` and close over the result. Policy changes apply on
the next reconnect.

| Surface                      | Rule                                                   |
| ---------------------------- | ------------------------------------------------------ |
| `list`                       | filtered to readable paths                             |
| `read`, opening a collab doc | requires `read`                                        |
| watch / change broadcasts    | withheld for unreadable paths                          |
| `write` (compare-and-swap)   | requires `write`                                       |
| collab edits (Y updates)     | refused without `write`; read-only peers still receive |
| media upload                 | requires `write` on `assets/<name>`                    |
| asset serving                | requires `read` on the asset path                      |
| presence identity            | a scope `user` overrides the name the client claims    |

A denied _path_ is a per-request error; the connection stays. A rejected
_hello_ closes the socket with a dedicated code. The client reports
`denied` (not `offline`) and stops retrying. Nothing is processed before
hello passes `authenticate`. Hello-less connections time out.

## Exposed data

A `read` reply (and the collab-open handshake) carries scope data for your
UI:

```ts
interface ReadResult {
  text: string;
  version: string;
  user?: { name: string; color?: string };
  writable?: boolean; // may this connection write this path
}
```

See [read-only](/read-only) for using `writable`.
