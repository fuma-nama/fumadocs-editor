## The trust model

Without an `authenticate` hook the sync server allows everything — the same
trust as Vite's own dev socket: anyone who can reach the dev server can edit
the files. That is the right default for local development and the wrong one
for anything shared. Passing `authenticate` puts every surface behind your
policy.

Enforcement is **server-only**. The client transports credentials and exposes
what the server decided as plain data — it never adjusts its own behavior.
Wiring "this user can't write" into a read-only editor is
[your code](/read-only), not a hidden mechanism.

## The two hooks

**Server**: `authenticate` maps a connection (or media request) to a scope,
or rejects it with `null`. It runs once per websocket connection — again on
every reconnect, so refreshed tokens apply — and once per HTTP media request.

**Client**: the transport's `auth` option produces an opaque payload, called
on every connection attempt. It rides the connection's first frame (browser
websockets can't set headers, and query strings leak into logs) and the
`x-fde-auth` header (`AUTH_HEADER`) on media requests. Cookie-based setups
simply omit it and read the request server-side.

## The scope contract

```ts
interface SyncScope {
  user?: { name: string; color?: string };
  read?: boolean | ((path: string) => boolean); // default true
  write: boolean | ((path: string) => boolean);
}
```

A document's identity is its root-relative posix path, so the predicates are
per-document permissions. Every predicate sees the **normalized** relative
path — `team-a/../outside.mdx` cannot smuggle a write past a `team-a/` rule.
The predicates run on the message hot path and must be synchronous: resolve
async policy inside `authenticate` (as in the token example) and close over
the result; policy changes apply on the next reconnect.

What the scope gates:

| Surface                      | Rule                                                     |
| ---------------------------- | -------------------------------------------------------- |
| `list`                       | filtered to readable paths                               |
| `read`, opening a collab doc | requires `read`                                          |
| watch / change broadcasts    | silently withheld for unreadable paths                   |
| `write` (compare-and-swap)   | requires `write`                                         |
| collab edits (Y updates)     | refused without `write` — read-only peers still receive  |
| media upload                 | requires `write` on `assets/<name>`                      |
| asset serving                | requires `read` on the asset path                        |
| presence identity            | a scope `user` overrides whatever name the client claims |

A denied _path_ is a per-request error — the connection stays. A rejected
_hello_ closes the socket with a dedicated code; the client reports the
terminal status `denied` (distinct from `offline`) and stops retrying.
Nothing is processed on a connection before its hello passes `authenticate`,
and hello-less connections time out.

## Exposed data

A `read` reply (and the collab-open handshake) carries scope-derived data for
your UI to use:

```ts
interface ReadResult {
  text: string;
  version: string;
  user?: { name: string; color?: string };
  writable?: boolean; // may this connection write this path
}
```

See [read-only wiring](/read-only) for putting `writable` to work.
