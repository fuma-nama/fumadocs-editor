A component without a spec already round-trips byte-for-byte: it renders as
a neutral card and is edited as source. A spec is what turns
`<Feature title="…">` into a block edited in place, with its own slash-menu
entry and attributes panel.

## Why a spec

The editor does not render your real components. Real components own state
and interactivity (tabs switch, accordions collapse, links navigate), which
fights an always-editable surface. Instead, each component gets two things:

- a **spec**: data describing how attributes and children map to editable
  regions
- a **renderer**: a lightweight mirror that draws the look around those
  regions

Because the spec is data, the editor can
[protect the structure](#what-the-guard-guarantees) no matter what the
renderer does.

## Regions

`children` in the render props is **all regions, in document order**: here
the `title` inline region, then the `body` block region. You place them
once; there is no separate slot per region.

- To style a region, target `data-region="<name>"` from the wrapper. The
  example bolds the title with `[&_[data-region=title]]:font-medium`.
- Mark chrome `contentEditable={false}` (the "Soon" badge) so the caret
  cannot enter it. Clicking chrome puts the caret in the nearest region.

## Props and literals

JSX attributes reach the renderer in two forms:

| Render prop | Holds                                  | Example                                  |
| ----------- | -------------------------------------- | ---------------------------------------- |
| `props`     | plain-string attributes                | `type="info"` → `props.type === "info"`  |
| `literals`  | static values of expression attributes | `soon={true}` → `literals.soon === true` |

`setProp(name, value)` writes a string attribute. `setLiteral(name, value)`
rewrites an expression from a literal value; the source text is derived.
Use them for controls the renderer owns, like the Callout type picker. An
expression that is not a static literal (a variable, a call) stays out of
`literals` and is edited as source in the attributes panel.

## What the guard guarantees

A structure guard runs on every transaction and heals anything that would
break a component's declared shape:

- A component always has exactly its declared regions. A paste that brings
  extra blocks is folded into the right region.
- Selections spanning region boundaries cannot tear a component into
  valid-but-wrong pieces, whether by typing, paste or delete.
- Structural moves only place components into parents whose
  `childComponent` accepts them. Invalid MDX cannot be produced.
- A renderer that throws degrades that one component to a fallback card
  with its regions still editable. The document stays lossless and siblings
  are untouched. Fixing the attribute heals it in place.
